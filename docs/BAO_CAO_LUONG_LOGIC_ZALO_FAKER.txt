BÁO CÁO LUỒNG LOGIC HỆ THỐNG ZALO_FAKER
========================================

Mục tiêu của file này:
- Giải thích luồng chạy bên dưới code theo cách dễ hiểu.
- Giúp bạn trình bày báo cáo môn học mà không cần đọc từng file code.
- Gồm cả phần công nghệ sử dụng, vì sao dùng, và nó nằm ở đâu trong hệ thống.

Lưu ý bảo mật:
- Không đưa nội dung file `.env` lên slide, GitHub, video demo hay nhóm chat.
- Trong `.env` có AWS key, Gemini key, JWT secret, email app password. Nếu đã lộ ra ngoài, nên đổi hoặc regenerate key.
- Khi báo cáo chỉ nói: "Hệ thống dùng biến môi trường để lưu key cấu hình", không show giá trị thật.


1. TỔNG QUAN HỆ THỐNG
=====================

Zalo_Faker là ứng dụng nhắn tin có các chức năng gần giống Zalo:
- Đăng ký, đăng nhập, OTP email, đổi mật khẩu, khóa/mở khóa tài khoản.
- Kết bạn, chấp nhận/từ chối lời mời, chặn/bỏ chặn.
- Chat cá nhân và chat nhóm realtime.
- Gửi text, ảnh, video, file, sticker, voice message.
- Reaction, đã đọc, đang nhập, thu hồi tin nhắn.
- Tạo nhóm, quản lý thành viên, vai trò, quyền nhóm, mã mời vào nhóm.
- Gọi audio/video cá nhân và gọi nhóm.
- Moments: đăng bài, reaction, bình luận, chia sẻ.
- Thông báo realtime.
- AI Assistant: hỏi đáp, lịch sử hỏi đáp, tóm tắt hội thoại.
- Transcript tin nhắn thoại bằng AI.

Kiến trúc tổng quát:

Người dùng
  -> Web app hoặc Mobile app
  -> Gọi REST API hoặc gửi Socket event
  -> Backend Express
  -> Controller
  -> Service
  -> Repository/Model
  -> DynamoDB / S3 / Redis / Gemini / Email
  -> Trả kết quả về client

Nói đơn giản:
- REST API dùng cho việc lấy/lưu dữ liệu rõ ràng: đăng nhập, lấy danh sách bạn bè, lấy lịch sử tin nhắn, tạo moment.
- Socket.IO dùng cho việc cần thấy ngay lập tức: tin nhắn mới, typing, đã đọc, online/offline, thông báo, cuộc gọi.
- DynamoDB dùng để lưu dữ liệu chính.
- S3 dùng để lưu file/media.
- Redis dùng để lưu session, OTP, trạng thái online tạm thời.
- Gemini dùng cho AI Assistant, tóm tắt chat, transcript voice.


2. CẤU TRÚC THƯ MỤC CHÍNH
=========================

server/
  index.js
    Điểm khởi động backend. Tạo app Express, gắn route, tạo HTTP server, cấu hình Socket.IO, kết nối Redis.

  routes/
    Khai báo các đường API. Ví dụ `/api/users`, `/api/messages`, `/api/groups`.

  controllers/
    Nhận request từ route, lấy tham số từ `req.body`, `req.params`, `req.user`, gọi service, trả response.

  services/
    Xử lý logic nghiệp vụ chính. Ví dụ đăng nhập, tạo tin nhắn, tạo nhóm, tạo moment, hỏi AI.

  repository/ và models/
    Làm việc với DynamoDB. Đây là lớp đọc/ghi dữ liệu.

  middlewares/
    authMiddleware.js: kiểm tra token JWT và session.
    upload.js: xử lý upload file bằng Multer.

  config/socket.js
    Xử lý tất cả realtime event: chat, typing, read, reaction, call, presence.

  utils/
    jwt.js: tạo và verify token.
    redisClient.js: kết nối Redis, có fallback memory.
    aws-helper.js: cấu hình AWS S3 và DynamoDB.
    sendEmail.js: gửi email OTP.

apps/web/
  React + Vite + TypeScript.
  Dùng cho giao diện web.

apps/mobile/
  React Native + Expo.
  Dùng cho ứng dụng mobile.


3. CÁC CÔNG NGHỆ SỬ DỤNG VÀ VAI TRÒ
===================================

Frontend Web:
- React: xây UI theo component.
- Vite: chạy dev/build nhanh.
- TypeScript: giúp code có kiểu dữ liệu rõ hơn.
- Tailwind CSS: viết giao diện nhanh bằng utility class.
- Zustand: quản lý state như user đăng nhập, danh sách chat, thông báo.
- React Router: điều hướng trang web.
- Socket.IO Client: kết nối realtime với backend.
- PeerJS/WebRTC: hỗ trợ gọi audio/video trên web.

Frontend Mobile:
- React Native: viết app mobile bằng React.
- Expo: hỗ trợ build/chạy app nhanh, quản lý camera, file, image picker, notification.
- Expo Router: điều hướng màn hình theo cấu trúc file.
- NativeWind: Tailwind style cho React Native.
- AsyncStorage/SecureStore: lưu token và dữ liệu cục bộ.
- Socket.IO Client: realtime chat/call/notification.
- React Native WebRTC: gọi audio/video trên mobile.

Backend:
- Node.js: môi trường chạy JavaScript phía server.
- Express: tạo REST API.
- Socket.IO: realtime hai chiều giữa client và server.
- JWT: xác thực bằng access token và refresh token.
- bcryptjs: hash mật khẩu.
- Multer: nhận file upload từ client.
- Nodemailer: gửi OTP qua Gmail.
- AWS SDK: làm việc với S3 và DynamoDB.
- Redis: lưu session, OTP, presence online/offline.
- LangChain + Google Gemini: AI Assistant, embedding, tóm tắt hội thoại.
- Swagger: tài liệu API.

Database/Storage:
- DynamoDB: lưu User, Conversation, Message, Friends, Moment, Notification, AI history...
- S3: lưu ảnh, video, file, avatar, media moment.
- CloudFront nếu cấu hình: tạo URL phân phối file nhanh hơn.

5. LUỒNG XÁC THỰC TOKEN
=======================

File liên quan:
- `server/middlewares/authMiddleware.js`
- `server/utils/jwt.js`
- `server/utils/redisClient.js`
- `server/services/userService.js`

Ý tưởng:
Backend không chỉ kiểm tra JWT có hợp lệ hay không, mà còn kiểm tra session trong Redis. Nhờ vậy nếu user logout, bị khóa tài khoản, hoặc đăng nhập thiết bị khác, server có thể từ chối request ngay.

Luồng API cần đăng nhập:
1. Frontend gửi request kèm header:
   `Authorization: Bearer <accessToken>`
2. authMiddleware lấy token từ header.
3. `verifyAccessToken` kiểm tra token có đúng secret và còn hạn không.
4. Lấy `userId` trong token.
5. Đọc user mới nhất từ DynamoDB.
6. Nếu `accountStatus` là locked/deleted thì từ chối.
7. Lấy `sessionId` trong token.
8. Kiểm tra `sessionId` có tồn tại trong Redis không.
9. Nếu hợp lệ thì gắn `req.user = thông tin user đã xác thực`.
10. Controller mới được xử lý tiếp.

Ví dụ dễ hiểu:
"JWT giống như vé vào cổng, còn Redis session giống như danh sách vé còn hiệu lực. Có vé nhưng vé đã bị hủy thì vẫn không vào được."


6. LUỒNG ĐĂNG KÝ TÀI KHOẢN
==========================

Route liên quan:
- POST `/api/users/register/request-otp`
- POST `/api/users/register/verify-otp`
- POST `/api/users/register/complete`

File liên quan:
- `server/routes/userRoutes.js`
- `server/controllers/userController.js`
- `server/services/userService.js`
- `server/utils/sendEmail.js`
- `server/repository/userRepository.js`

Luồng:
1. User nhập email trên màn hình đăng ký.
2. Frontend gọi API request OTP.
3. Backend kiểm tra email hợp lệ và chưa tồn tại.
4. Backend tạo OTP 6 số.
5. OTP được lưu tạm vào Redis, có thời hạn.
6. Backend gửi OTP qua Gmail bằng Nodemailer.
7. User nhập OTP.
8. Backend so sánh OTP user nhập với OTP trong Redis.
9. Nếu đúng, backend đánh dấu email đã verify tạm thời.
10. User gửi thông tin hoàn tất đăng ký: email, mật khẩu, tên, số điện thoại...
11. Backend hash mật khẩu bằng bcrypt.
12. Backend tạo user mới trong DynamoDB.
13. Trả về kết quả đăng ký thành công.

Điểm hay để trình bày:
- OTP không lưu vĩnh viễn, chỉ lưu tạm bằng Redis.
- Mật khẩu không lưu dạng plain text, mà lưu bản hash.
- Đăng ký tách thành nhiều bước để tránh tạo tài khoản khi email chưa được xác thực.


7. LUỒNG ĐĂNG NHẬP
==================

Route:
- POST `/api/users/login`

Luồng:
1. User nhập email/số điện thoại và mật khẩu.
2. Frontend gọi API login.
3. Backend tìm user theo email hoặc số điện thoại.
4. Nếu không có user thì báo lỗi.
5. Nếu user bị khóa/xóa thì không cho đăng nhập.
6. Backend dùng `bcrypt.compare` để so sánh mật khẩu.
7. Nếu đúng, backend tạo `sessionId`.
8. Backend tạo access token và refresh token bằng JWT.
9. Backend lưu `sessionId` vào Redis theo user + platform.
10. Backend lưu refresh token vào DynamoDB.
11. Backend lưu login history.
12. Trả user + token về frontend.
13. Frontend lưu token vào store/local storage.
14. Frontend kết nối Socket.IO bằng access token.

Access token:
- Hạn ngắn, dùng để gọi API.

Refresh token:
- Hạn dài hơn, dùng để xin access token mới.

Session Redis:
- Dùng để ép logout, quản lý đăng nhập theo web/mobile, tránh token cũ vẫn dùng mãi.


8. LUỒNG REFRESH TOKEN
======================

Route:
- POST `/api/users/refresh-token`

Luồng:
1. Frontend gọi API bình thường.
2. Nếu backend trả 401 vì access token hết hạn, frontend dùng refresh token để xin token mới.
3. Backend kiểm tra refresh token có tồn tại trong DB không.
4. Backend verify refresh token.
5. Nếu hợp lệ, tạo access token mới.
6. Frontend lưu access token mới.
7. Frontend gọi lại request ban đầu.

Web app dùng `fetchWithAuth` để tự động refresh.
Mobile app dùng axios interceptor để tự động refresh.

Giải thích dễ hiểu:
"Access token là thẻ ra vào ngắn hạn. Khi hết hạn, refresh token giống như giấy gia hạn để xin thẻ mới mà không bắt user đăng nhập lại."


9. LUỒNG ĐĂNG XUẤT VÀ ÉP ĐĂNG XUẤT
==================================

Đăng xuất:
1. User bấm logout.
2. Frontend gọi API logout kèm refresh token.
3. Backend xóa refresh token khỏi DB.
4. Backend xóa session trong Redis nếu có.
5. Frontend xóa token local và disconnect socket.

Ép đăng xuất:
1. Khi user đăng nhập cùng nền tảng, ví dụ 2 web session khác nhau.
2. Socket server phát hiện session mới.
3. Server emit event `session:force_logout` đến socket cũ.
4. Client cũ hiện thông báo và logout.

Điểm để nói:
"Hệ thống không chỉ login/logout trên client, mà server cũng quản lý session nên có thể vô hiệu hóa phiên đăng nhập cũ."

4. Backend verify OTP.
5. Nếu đúng, backend đánh dấu email đã verify trong Redis.

11. LUỒNG KHÓA/MỞ KHÓA TÀI KHOẢN
================================

Chức năng:
- Khóa tài khoản tạm thời.
- Khóa vĩnh viễn cần OTP.
- Mở khóa tài khoản.

Luồng khóa tạm thời:
1. User đăng nhập vào cài đặt bảo mật.
2. Nhập mật khẩu hiện tại.
3. Backend so sánh mật khẩu.
4. Nếu đúng, cập nhật `accountStatus = locked`.
5. Các request mới sẽ bị authMiddleware chặn.

Luồng khóa vĩnh viễn:
1. User yêu cầu OTP khóa vĩnh viễn.
2. Backend gửi OTP qua email.
3. User nhập mật khẩu + OTP + xác nhận.
4. Backend verify mật khẩu và OTP.
5. Cập nhật tài khoản sang trạng thái deleted/locked theo logic.
6. Xóa refresh token để phiên cũ không dùng được nữa.

Luồng mở khóa:
1. User vào màn hình unlock.
2. Nhập email và mật khẩu.
3. Backend kiểm tra user và mật khẩu.
4. Nếu hợp lệ, cập nhật lại `accountStatus = active`.


12. LUỒNG QR LOGIN
==================

Route:
- POST `/api/users/qr-login/session`
- GET `/api/users/qr-login/session/:sessionId/status`
- POST `/api/users/qr-login/confirm`

Ý tưởng:
Web tạo QR. Mobile đã đăng nhập quét QR và xác nhận. Sau đó web nhận token đăng nhập.

Luồng:
1. Web gọi API tạo QR session.
2. Backend tạo `sessionId`, `confirmCode`, `pollToken` và lưu Redis khoảng 120 giây.
3. Web hiện QR có chứa `sessionId` và `confirmCode`.
4. Mobile đã đăng nhập quét QR.
5. Mobile gọi API confirm kèm token của user mobile.
6. Backend kiểm tra QR session còn hạn và `confirmCode` đúng.
7. Backend tạo login session mới cho nền tảng web.
8. Web liên tục poll status bằng `sessionId + pollToken`.
9. Khi status confirmed, web nhận auth token và đăng nhập.

Nói đơn giản:
"QR login dùng Redis để lưu phiên tạm thời. Mobile xác nhận xong thì web lấy token từ phiên QR đó."

15. LUỒNG GỬI TIN NHẮN REALTIME
===============================

File quan trọng:
- `apps/web/src/lib/socket.ts`
- `apps/mobile/src/lib/socket.ts`
- `server/config/socket.js`
- `server/services/messageService.js`
- `server/models/message.js`
- `server/models/conversation.js`

Socket event:
- `chat:send`
- `chat:message`
- `chat:conversation_updated`

Luồng chi tiết:
1. User gõ nội dung và bấm gửi.
2. Frontend tạo payload:
   - `conversationId`
   - `type`: text/image/video/file/voice/sticker/poll/call
   - `content`
   - `attachments`
   - `replyTo`
   - `metadata`
3. Frontend emit socket event `chat:send`.
4. Socket server lấy `userId` từ socket đã xác thực.
5. Server kiểm tra `conversationId` có tồn tại.
6. Server kiểm tra user có là thành viên conversation không.
7. Nếu là chat nhóm:
   - Kiểm tra quyền gửi tin/gửi media/gửi announcement.
8. Nếu là chat cá nhân:
   - Kiểm tra quan hệ chặn/bỏ chặn.
9. Nếu là poll:
   - Chuẩn hóa nội dung poll.
   - Chỉ cho poll trong group.
10. Server gọi `messageService.createMessage`.
11. messageService lưu message vào DynamoDB.
12. Nếu message type voice, đánh dấu `transcriptStatus = processing`.
13. Nếu là voice, chạy transcript nền bằng Gemini.
14. Server cập nhật `lastMessage` của conversation.
15. Server emit `chat:message` đến các user khác trong room.
16. Server trả ACK về user gửi với message đã lưu thật.
17. Client thay temp message bằng message thật nếu có `clientTempId`.
18. UI cập nhật tin nhắn và last message.

Giải thích cực ngắn:
"Khi gửi tin nhắn, client không gửi cho từng người riêng lẻ. Client gửi lên server, server lưu database, rồi phát lại cho các thành viên trong room."

==============================

Luồng:

17. LUỒNG TYPING, ĐÃ ĐỌC, REACTION
==================================

Typing:
1. User đang gõ chữ.
2. Client emit `chat:typing`.
3. Server kiểm tra user có trong conversation.
4. Server emit `chat:typing` cho các user khác trong room.
5. UI hiện "Đang nhập...".

Stop typing:
1. User ngừng gõ.
2. Client emit `chat:stop_typing`.
3. Server phát event cho các user khác.

Đã đọc:
1. User xem đến một tin nhắn.
2. Client emit `chat:read` với `messageId`.
3. Server kiểm tra message thuộc conversation.
4. Server thêm `userId` vào `readBy`.
5. Server emit `chat:read` cho room.
6. UI cập nhật dấu đã đọc.

Reaction:
1. User chọn emoji cho tin nhắn.
2. Client emit `chat:reaction`.
3. Server cập nhật reactions trong message.
4. Server emit message đã update cho room.
5. UI hiện emoji reaction.


18. LUỒNG THU HỒI VÀ XÓA TIN NHẮN
=================================

Thu hồi tin nhắn:
1. User chọn thu hồi.
2. Client emit `chat:recall`.

23. LUỒNG QUẢN LÝ QUYỀN NHÓM

- deputy: phó nhóm.
- member: thành viên thường.

5. Lấy `settings.permissions`.
6. Nếu message là media thì kiểm tra `sendMedia`.
7. Nếu là announcement thì kiểm tra `sendAnnouncement`.
8. Nếu là text/poll thì kiểm tra `sendMessage`.

10. Nếu đủ quyền, message được lưu và phát realtime.

31. LUỒNG ONLINE/OFFLINE PRESENCE
=================================

File:
- `server/config/socket.js`
- `server/utils/redisClient.js`
- `server/repository/userRepository.js`

Luồng khi user online:
1. Client connect Socket.IO kèm access token.
2. Socket middleware verify token và session.
3. Server gắn `socket.userId`.
4. Socket join room riêng: `user:<userId>`.
5. Server lưu presence key vào Redis:
   `presence:<userId>:<platform>`
6. Key có TTL khoảng 90 giây.
7. Server cập nhật user `presenceStatus = online` trong DB.
8. Server broadcast `presence:online`.
9. Định kỳ heartbeat refresh TTL.

Luồng khi disconnect:
1. Socket disconnect.
2. Server xóa presence key nếu socketId trùng.
3. Kiểm tra user còn socket nào online không.
4. Nếu không, cập nhật `presenceStatus = offline` và `lastActiveAt`.
5. Broadcast `presence:offline`.

Nói đơn giản:
"Online/offline không chỉ dựa vào database, mà dùng Redis TTL để tránh trường hợp app tắt đột ngột mà trạng thái bị treo online mãi."

44. CÁC CÂU HỎI THƯỜNG GẶP VÀ CÁCH TRẢ LỜI
==========================================

Hỏi: Tại sao không dùng REST API để gửi tin nhắn?
Trả lời:
"REST API vẫn gửi được, nhưng người nhận sẽ không thấy ngay nếu không polling liên tục. Socket.IO giúp server đẩy tin mới đến client ngay khi tin được lưu."

Hỏi: Tin nhắn có được lưu trữ không?
Trả lời:
"Có. Socket chỉ dùng để realtime. Sau khi gửi, server lưu message vào DynamoDB, cập nhật lastMessage, rồi mới emit cho các client."

Hỏi: Nếu user mất kết nối thì sao?
Trả lời:
"Socket client có reconnect. Khi reconnect, client join lại các room đã tham gia. Presence online/offline được quản lý bằng Redis TTL để tránh bị treo trạng thái."

Hỏi: Token hết hạn thì sao?
Trả lời:
"Frontend có logic refresh token. Nếu access token hết hạn, client dùng refresh token để xin access token mới và retry request."

Hỏi: Logout rồi token cũ có dùng được không?
Trả lời:
"Không nên dùng được nữa, vì backend không chỉ verify JWT mà còn kiểm tra sessionId trong Redis. Nếu session bị xóa thì request bị từ chối."

Hỏi: File upload lưu ở đâu?
Trả lời:
"File lưu trên AWS S3. Backend trả về URL, message/moment/avatar chỉ lưu URL đó trong database."

Hỏi: AI có đọc toàn bộ database không?
Trả lời:
"Không. Backend chỉ đưa vào AI những dữ liệu cần thiết như thông tin user hiện tại, context hội thoại liên quan, và tài liệu hướng dẫn. AI không tự truy cập database trực tiếp."

Hỏi: Gọi video có qua server không?
Trả lời:
"Server dùng Socket.IO để signaling. Audio/video chính dùng WebRTC giữa các client. Với group call, server quản lý phòng và danh sách thành viên."

Hỏi: Nhóm có phân quyền không?
Trả lời:
"Có. Mỗi participant có role admin, deputy, member. Group settings quy định ai được gửi tin, gửi media, bắt đầu call, ghim tin và gửi announcement."

============

Điểm mạnh của hệ thống:
- Có kiến trúc phân lớp rõ: route -> controller -> service -> repository/model.
- Có realtime thật bằng Socket.IO.
- Có bảo mật session kết hợp JWT và Redis.
- Có lưu trữ file riêng trên S3.
- Có AI tích hợp vào nghiệp vụ chat.
- Có cả web và mobile dùng chung backend.

Khi báo cáo, nên nhấn mạnh:
1. Luồng realtime của chat.
2. Bảo mật đăng nhập/session.
3. Quản lý nhóm có role/permission.
4. Upload media qua S3.
5. AI Assistant dùng context thật từ hệ thống.
